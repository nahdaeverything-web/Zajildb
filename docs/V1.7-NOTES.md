# v1.7 — what I left inconsistent, and where the structure will fight you

Report only. Nothing here was changed in this pass.

---

## 1. Things left inconsistent

### 1.1 A user's pre-v1.7 export still violates the ownership invariant
`newBird()` now guarantees `external === (status === REFERENCE_STATUS)`, and
both shipped datasets were regenerated to match. But `importAll` is the force
path — it lands records verbatim by design — so **an export taken before v1.7
will import external birds carrying `status: 'stock'`.**

The data-level guard test asserts the invariant for factory-created birds and
for the shipped datasets, *not* for arbitrary imported data, because asserting
it there would mean rejecting or silently rewriting the user's own file.

Normalising on import is a **data migration** and is your call. Options:
- normalise silently on import (changes user data without asking);
- normalise and report ("12 ancestors were re-labelled");
- add a one-off "repair data" action in Tools alongside the integrity check;
- leave it, and let the register's ownership filter be slightly wrong for old data.

### 1.2 `checkIntegrity` is not run automatically
It is exposed in the dev panel and asserted in tests, but nothing calls it on
boot or after an import. It is a check, not an enforcement. Running it on
import and surfacing the result would be cheap; I did not add it because it
changes import behaviour and you asked for no unrequested scope.

### 1.3 `CROSS_REFERENCES` needs manual extension
Stated in a comment block in `js/engine/integrity.js` and repeated here: adding
a store or a cross-record field requires adding it to that table. Nothing
detects a reference the table does not know about. This is the one piece of
ongoing upkeep the design does not eliminate.

### 1.4 `makeGeneric` stores have no validation boundary
`saveBird` validates. `Pairs.save` / `Races.save` / `Health.save` / `Lofts.save`
do not — there is no `validatePair` equivalent beyond `validatePairSexes`,
which is still called from the view. Symmetry would mean a `classifySave` for
each store. Not done: out of scope, and it needs rules that do not exist yet.

### 1.5 One guard is narrower than its name suggests
"no view writes to IndexedDB directly" scans for the `idbPut`/`idbDelete`/
`idbClear` identifiers. A view could still reach storage via
`(await import('./db.js'))['idb'+'Put']` or by opening its own connection. That
is defeat-by-deliberate-effort, not the accident the guard exists to catch. I
did not widen it, because every broader pattern I tried also matched db.js's
own legitimate internals and would have had to be loosened to pass — which you
explicitly asked me not to do.

### 1.6 No guard forbids `new Date(iso)` for date-only strings
`js/dates.js` owns parsing, and `fmtGregorian`/`fmtHijri` route through it, but
a future view could still call `new Date('2026-03-14')` and render a day early
west of Greenwich. `new Date(` is far too common to scan for. The mitigation is
that all *display* funnels through `fmtDate` in i18n.js.

## 2. Where the current structure will fight a server-backed data layer

You said you intend to build on top of this. These are the places that will
resist, with no change made.

### 2.1 `getBird` is synchronous, and the engine depends on that
`js/engine/` takes a `getBird(id)` callback and calls it thousands of times
inside recursive COI traversals. `db.js` keeps `state.birds` as an in-memory
`Map` precisely so that callback can be synchronous.

A server-backed layer cannot answer synchronously. You would face a fork:
- keep a full local mirror and sync it (the engine is untouched — cheapest, and
  what the local-first design already implies); or
- make the engine async, which means every COI path becomes `await`-ed and the
  memoisation and path enumeration in `coi.js` get substantially harder.

**The first option is strongly preferable and the current design already
points at it.** Worth deciding before building, because it is not cheap to
reverse.

### 2.2 `stamp()` sets `updatedAt` from the device clock
Fine for per-field last-write-wins as documented, but two devices with skewed
clocks will resolve conflicts wrongly, and a device with a wrong date can
"win" every conflict permanently. A server-backed layer usually wants a
server-assigned version or a logical clock. The field is in place; its
semantics are the open question.

### 2.3 IDs are client-generated UUIDs
Good for offline creation and merge (no coordination needed). But nothing
prevents two devices creating *semantically the same bird* — the same ring
number entered twice — as two records with different ids. The duplicate finder
catches it after the fact; a sync layer would meet it constantly. Ring number
is the natural business key but is explicitly **not** the identity, for good
reasons documented in the handoff.

### 2.4 `importAll` is the only bulk-write path, and it is all-or-nothing
Now correctly atomic, but it is a *whole-database replace or merge*. A sync
layer needs incremental, per-record application with conflict resolution.
`importAll` is not that shape and should not be bent into it.

### 2.5 The change event carries no payload
`emitChange({type, id})` says *something* changed. The subscriber re-routes and
re-reads everything. That is fine at loft scale and genuinely simple. A
server-backed layer pushing deltas would want the changed record on the event
so views can patch rather than re-render.

### 2.6 `loftId` is stamped but never enforced
Every record carries it, and nothing filters by it. `allBirds()` returns every
bird regardless of loft. Club mode — one admin over several member lofts — will
need that filter at the boundary, and adding it later means auditing every
`state.*` read site. Cheap now, tedious later.

## 3. Backlog items this pass resolved as a side effect

Fixed structurally rather than one by one:
- UTC date defaults recording yesterday (breeding, health) — phase 1.1
- date-only values rendering a day early at negative offsets — phase 1.1
- "ring chick" bypassing validation entirely — phase 1.2
- the link-existing path applying `hatchDate` after validation — phase 1.2
- undo of a bird deletion not refreshing the register — phase 1.3
- undo of a media deletion doing nothing visible, and throwing on a double delete — phase 1.3
- deleting a bird orphaning race results, health events and pairs — phase 1.4
- ancestors created inline getting status 'stock' — phase 1.5
- add-sibling committing the parent rewrite before the sibling exists — phase 1.5
- every automatic snapshot base64-encoding all photos then discarding them — phase 3
- replace-import erasing the database before decoding the payload — phase 3

Still open in BACKLOG.md and untouched, since they are genuinely individual
defects rather than symptoms of a missing primitive: the FCI column marking
results as qualifying for birds with no FCI ring; Statistics recomputing COI
per bird and freezing the UI; the same bird linkable as the chick of two eggs;
photo inputs accumulating rather than replacing; the coordinate parser
mis-reading DMS input; and the register showing a blank list rather than a
"no matches" state.
